Context guide for Claude (Code/Cowork) working in this repository. Read this file before proposing or applying any change to the project.

## Overview

Sharingan is a Python pentest/reconnaissance framework, inspired by Metasploit (msfconsole). The project is an msf-style interactive console (REPL), with database persistence via SQLAlchemy, organized by **pentest methodology phases** (recon, scan, vulnerability analysis, ...) instead of a single script.

Product goals:
- msfconsole-style interactive console (commands, `options`, `set`, `whois`, `scan`, etc.).
- Surface scan: port discovery + service/version fingerprinting + correlation with known exploits.
- Continuous service-availability monitoring (TCP).
- Possible future web layer (API/dashboard) — not started yet.

Architecture principle adopted on 2026-08-29: **don't reimplement tools that already exist and are the reference in the field.** The Scan phase has no port scanner of its own — it orchestrates `rustscan` (fast discovery), `nmap -sV` (product/version fingerprinting), and `searchsploit` (exploit-db) as external processes, and persists the structured result to the database. The same principle applies to future phases: prefer orchestrating a mature community tool over writing an in-house version, unless no reasonable option exists.

Important note on the rustscan/nmap division of labor (source: RustScan's official documentation and wiki): **RustScan does not do service/version fingerprinting** — it only discovers open ports fast (that's the whole reason it exists: sweeping all 65535 TCP ports much faster than nmap alone would). Product/version identification is always done by `nmap -sV`, run only on the ports rustscan found open. They aren't two competing tools — it's fast discovery feeding deep inspection. User decision (2026-08-29): keep both mandatory (a configurable "choose your scanner" isn't worth it right now, since they aren't interchangeable), and when an external tool (`rustscan`/`nmap`/`searchsploit`) isn't found, the console asks the user whether to install it and installs it automatically when possible (see `ToolInstaller` under "Phase architecture").

Vulnerability correlation (user decision, 2026-08-29, in response to "is there a more efficient way than searchsploit?"): nmap's `vulners` NSE script matches CPE (product/version) against the public vulners.com API and returns CVE+CVSS directly, with no meaningful extra execution cost — it runs embedded in the same `nmap -sV` call already made for fingerprinting, it isn't a separate call. That's why the order is **vulners first (CVE+CVSS via CPE, more precise), searchsploit afterward only for the relevant findings** (CVSS >= `min_cvss`, default 7.0): if vulners doesn't find anything relevant, `searchsploit` doesn't even run; if `vulners` isn't installed (it's a `.nse` script, not an OS package), behavior falls back to the previous one — `searchsploit` always runs whenever available, without that filtering.

## Stack

- Python >= 3.12, managed with `uv` (`uv.lock`, `pyproject.toml` in a workspace).
- SQLAlchemy 2.x + local SQLite (`sharingan.db`); `DATABASE_URL` configurable via environment variable.
- `prompt_toolkit` + `rich` for the CLI/REPL.
- `requests` + `beautifulsoup4` (bs4) for the HTML spider.
- `scapy` for ARP scanning.
- `python-whois` for whois lookups.
- `pytest` + `pytest-mock` for tests (dev dependencies).
- **External tools (not Python packages — must be on the system's PATH):** `rustscan`, `nmap`, `searchsploit` (`exploitdb` package) **+ `xmllint`** (`libxml2-utils` package on Debian/Ubuntu, `libxml2` on Fedora/Arch/Homebrew — required for the `searchsploit --nmap` mode we use; without it the process exits with status 1, see "Current state"), and optionally nmap's own `vulners` NSE script. Needed only for the console's `scan` command; the rest of the framework works without them. Installation: `nmap` and `exploitdb` have a reliable package via apt/dnf/pacman/brew (`exploitdb` is the official package name, including on Kali). **RustScan has no apt/dnf/pacman package on any mainstream distro** (confirmed — not even Kali packages it) — the official methods are `cargo install rustscan`, Homebrew on macOS, or downloading the `.deb` from the GitHub releases page and installing it with `dpkg -i`. `ToolInstaller` (`phases/scan/tools/installer.py`) only tries the install paths that actually exist; for rustscan that's cargo/brew, with everything else falling back to a manual instruction. **`vulners` has no automated install of its own** — it's normally a standalone `.nse` file (clone `https://github.com/vulnersCom/nmap-vulners`, copy it into nmap's script folder, and run `nmap --script-updatedb`) —, **but it was confirmed by testing (2026-08-30) that Ubuntu/Debian's apt `nmap` package already ships `vulners.nse` embedded in the default script database** (`nmap --script-help vulners` works right after an `apt install nmap`, with no manual step at all). In other words, in practice anyone who installs `nmap` via apt on Ubuntu/Debian (and probably Kali) already has `vulners` available for free — the yellow "vulners not found" warning should only show up on distros/builds that don't package that script.

- **Real bug found in use (2026-08-29): `RustscanTool.scan_ports` passed the `--no-nmap` flag, which no longer exists in current RustScan** (confirmed in the official source, `src/input.rs`, and in the open issue "Bring back --no-nmap!" #650 on the RustScan repo asking for it to be reintroduced). A flag `clap` (Rust's CLI parser) doesn't recognize makes the process exit with status 2 (usage error), which `subprocess.run(..., check=True)` turns into a `CalledProcessError` — this was exactly the `Error during scan: Command [...] returned non-zero exit status 2` the user saw running `scan` for real. Fixed by removing `--no-nmap` from the command: `-g/--greppable` alone is already enough (it's the whole reason it exists — it just prints `host -> [ports]`, without running rustscan's embedded nmap). A regression test in `test_rustscan_tool.py` (`test_scan_ports_does_not_pass_removed_no_nmap_flag`) ensures the flag doesn't come back.
- **Real UX issue found in use (2026-08-30): after the rustscan fix, the user ran a real scan and asked "where's the vulners/searchsploit result?" — the screen showed nothing beyond the ports table.** Cause: with no vulnerability or exploit found, the console simply printed nothing about those two steps — making it impossible to tell "it ran and found nothing" apart from "it never even ran". Fixed in two parts: (1) `ScanPhase.run` now records `self.last_vulners_enabled` and `self.last_searchsploit_ran` (bool) on every run, reflecting whether each step actually ran; (2) `handle_scan` uses these flags to always give an explicit response — "No relevant vulnerabilities found (vulners)." when vulners ran and found zero; "No matching exploit found in searchsploit." when searchsploit ran and found zero; "searchsploit did not run — vulners found nothing relevant..." when searchsploit was skipped by design (vulners available but nothing with CVSS above the minimum). See the new tests in `test_scan_phase.py` (`test_scan_phase_records_last_run_flags_*`) and `test_console.py` (`test_command_scan_shows_message_when_*`).
- **Real bug found in use (2026-08-30): `searchsploit --nmap ... -j` exited with `Command [...] returned non-zero exit status 1`, taking down the whole scan** (even with ports/services already persisted by nmap). Cause confirmed by testing: `searchsploit --nmap` depends on `xmllint` to parse the nmap XML — without it, the process prints `[!] Please install xmllint` and exits with status 1 (a known requirement of the tool, not a bug of ours: see Sn1per issue #72, "kali needs xmllint for sniper's call to searchsploit"). The user had `searchsploit` in PATH (installed outside apt's `exploitdb`, likely just via a manual repo clone), but without `xmllint`/`libxml2-utils` — our old check (`is_available()`) only looked at the `searchsploit` binary, so it found the tool "available" and never offered to install anything. Fixed in three parts: (1) `SearchsploitTool.is_available()` now also requires `shutil.which('xmllint')`, so its absence now triggers the normal ask-and-install flow; (2) `ToolInstaller.install_searchsploit()` installs `exploitdb` **and** the package that provides `xmllint` together (`libxml2-utils` on apt, `libxml2` on dnf/pacman/brew); (3) **defense in depth** — even if `is_available()` gave a false positive for some other reason, `ScanPhase.run` now wraps the call to `searchsploit` in a `try/except subprocess.CalledProcessError`: a runtime failure becomes `self.last_searchsploit_error` (a string) instead of propagating and taking down the rest of the scan — searchsploit is an optional/best-effort step, and a failure in it should never throw away the nmap fingerprint that was already persisted. The console shows this error explicitly (`"searchsploit failed to run: ..."`) instead of pretending nothing was found. Tests: `test_searchsploit_tool.py` (`test_is_available_false_when_xmllint_missing`), `test_scan_phase.py` (`test_scan_phase_survives_searchsploit_runtime_failure`), `test_console.py` (`test_command_scan_shows_message_when_searchsploit_fails_at_runtime`).
- **Real bug found in use (2026-08-30): running `scan` again on the same host duplicated ports/services and CVEs on every run** (the user reported seeing the same port and the same CVE repeated 4-5 times after running `scan` several times against `127.0.0.1`: "The system is duplicating ports and services every time we run against the same host. It looks like there's no host:services relationship."). Cause: `ScanPhase._get_or_create_host` already correctly reused the existing `Host` by `addr` (no `Host` duplication there), but `_persist_services` only ever did an `INSERT` — it never cleared that host's `Service` rows (and, as a consequence, `Vulnerability`/`ExploitMatch`) from the previous scan before writing the new ones, so every re-scan stacked a whole new set on top of the old one. Fixed with the principle "the newest scan is the host's most current snapshot": `ScanPhase._clear_previous_scan_data(host)` now deletes all of that host's `Service` rows **at the start of `run()`**, before anything else (including before checking for open ports — important so the case "a host that used to have open ports and now doesn't" also clears what's now stale). This only works correctly with **cascade delete** configured in `model/service_model.py`: by default, when SQLAlchemy deletes a parent `Service`/`Host`, it only nulls the children's FK (`Vulnerability.service_id`/`ExploitMatch.service_id`, or `Service.host_id`) instead of deleting them — which raises an `IntegrityError` (`NOT NULL constraint failed`) because those columns are `nullable=False`. Added `cascade='all, delete-orphan'` via `sqlalchemy.orm.backref` on the three relationships (`Service.host`, `Vulnerability.service`, `ExploitMatch.service`), confirmed with dedicated tests in `tests/test_service_model.py` (`test_deleting_host_cascades_to_its_services`, `test_deleting_service_cascades_to_its_vulnerabilities_and_exploit_matches`, `test_deleting_host_cascades_all_the_way_to_vulnerabilities_and_exploits`) before touching `ScanPhase`. Regression tests for the duplication itself: `test_scan_phase.py` (`test_scan_phase_rescan_replaces_previous_services_instead_of_duplicating`, `test_scan_phase_rescan_with_no_open_ports_clears_stale_services`). This same cascade delete is what makes it safe to delete Host/Service/Vulnerability through the new `hosts -d`/`services -d`/`vulns -d` commands (see below) without leaving orphaned junk in the database.

- **Real bug found in use: `scan` against a Redis target (vulhub's `redis:5.0.7`, `CVE-2022-0543` lab) showed "No matching exploit found in searchsploit" even though `searchsploit redis`, run by hand, lists 5 real matching exploits** (`Redis - Replication Code Execution`, `Redis 4.x / 5.x - Unauthenticated Code Execution`, etc.). Confirmed by reproducing the exact `searchsploit --nmap <xml> -j` call `SearchsploitTool.search_nmap_xml` makes against a real `nmap -sV` XML for that target: `searchsploit --nmap` does **not** print one JSON document on stdout — for each detected service it retries the search with progressively more specific terms derived from nmap's own product/version fingerprint (here: `redis`, then `redis key value store`, then `redis key value store 5.0.7`), printing one JSON object per attempt, all concatenated with no separator. The first, broadest attempt found the 5 real matches; the narrower, version-qualified ones that followed found none — and `SearchsploitTool._parse_json` did `json.loads()` on the *entire* concatenated stdout, which raises `JSONDecodeError: Extra data` the moment there's more than one object, silently discarded via a bare `except json.JSONDecodeError: return []`. In other words: **any scan whose nmap XML has a specific enough version fingerprint to trigger more than one internal `--nmap` search attempt lost 100% of its real matches**, not just Redis — this wasn't Redis-specific. Fixed by rewriting `_parse_json` to decode the stdout as a stream of concatenated JSON objects (`json.JSONDecoder().raw_decode()` in a loop) and merge their `RESULTS_EXPLOIT`, deduplicated by `EDB-ID` (the same broad search can repeat once per matched service in a multi-service/multi-host scan). Tests: `test_searchsploit_tool.py` (`test_search_nmap_xml_merges_multiple_concatenated_json_objects`, `test_search_nmap_xml_deduplicates_matches_by_edb_id_across_json_objects`) — the first one's fixture data and docstring record the exact real-world repro (product/version strings, search terms, EDB-IDs) so the scenario doesn't need re-deriving next time this file is touched.

**Scan history via `ScanRun` (2026-10-02).** Supersedes the "newest scan wipes the previous one" behavior described above (`ScanPhase._clear_previous_scan_data` no longer exists). Each `scan` creates a `ScanRun` (`model/service_model.py`: `host_id`, `started_at`, `finished_at`, `status` = running/ok/failed) and every `Service` (and, through it, `Vulnerability`/`ExploitMatch`) it finds carries that `scan_run_id`; previous runs stay as history. Because rows now accumulate, **never query a host's services by `host_id` alone** — use `current_services_filter()` (same file), which selects each host's latest non-failed run (or legacy `scan_run_id IS NULL` rows when the host has no runs). `ScanPhase.run` marks the run `failed` and re-raises if a step throws, so a broken scan never hides the last good result. `Service.scan_run_id` is nullable and added to existing databases by `db/migrations.py`. Known follow-up: `services -d <addr>` / `vulns -d <addr>` delete across *all* runs of the host (history included); reading the history is done: `scans [addr]` lists runs (id/host/status/duration/service count) and `scan diff <addr>` compares the host's last two **finished** (`ok`) runs — opened/closed ports, version changes, new/resolved CVEs — via the pure function `diff_scan_runs` in `phases/scan/scan_diff.py` (so `diff` can't be used as a scan name). Tests: `test_scan_diff.py`, `test_console.py` (`test_command_scans_*`, `test_command_scan_diff_*`). Next in `docs/roadmap-asm.md`: scope (`Target`), asset discovery, alerts. Tests: `test_service_model.py` (`ScanRun`, `current_services_filter`), `test_scan_phase.py` (`test_scan_phase_*scan_run*`, rescan cases), `test_console.py` (`*_shows_only_the_latest_scan_run`).

**Scope (`scope` command, 2026-10-02).** `ScopeRule` (`model/scope_model.py`: `kind` domain/ip/cidr, normalized unique `value`, `allow` include/exclude) + the pure matcher in `core/scope.py` (`parse_scope_value`, `decide`). `scope` lists; `scope add|exclude <value>` upserts (re-adding a value flips it); `scope remove <value>`. Rules: a domain rule covers the apex and its subdomains on label boundaries (`badexample.com` is NOT covered); matching is **literal, no DNS resolution** (a hostname only matches domain rules, an IP only ip/cidr rules); **exclusions always win**; with **no include rules scope is unrestricted** (so existing workflows don't break) and `scan` prints a yellow "No scope defined" notice. `handle_scan` calls `_target_allowed_by_scope` before creating the `ScanPhase`, so a blocked target generates no traffic and no `Host`/`ScanRun`. Enforcement lives in the console, not in `ScanPhase`: any future phase's console handler (web crawl, dir enumeration) must call the same check. The legacy `core/spider_core.py` substring-regex "scope" was NOT migrated (it's only used by the unsupported legacy CLI). Tests: `test_scope.py`, `test_console.py` (`test_scope_*`, `test_scan_is_blocked_*`), `test_database.py`.

## Phase architecture (`phases/`)

Each phase of the pentest methodology is a module that implements `PhaseModule` (`phases/base.py`): it defines `name`, `description`, and a `run(**options)` method. The idea is the same as Metasploit's modules — a uniform interface for the console to discover and run phases, regardless of what each one does underneath.

The first phase implemented is `ScanPhase` (`phases/scan/scan_phase.py`):

```
rustscan (port discovery)
   -> nmap -sV [+ --script vulners when available] (product/version fingerprinting, only on open ports)
      -> vulners (reads CVE/CVSS from the same nmap XML, matching by CPE — only if the script is installed)
         -> searchsploit --nmap (matches product/version against exploit-db — whenever vulners is unavailable;
                                   when vulners is available, only runs if it found something with CVSS >= min_cvss)
            -> persists Host / Service / Vulnerability / ExploitMatch to the database
```

Each external tool has a thin wrapper in `phases/scan/tools/` (`RustscanTool`, `NmapTool`, `VulnersTool`, `SearchsploitTool`), each with `is_available()` (checks the binary on PATH via `shutil.which`; `VulnersTool.is_available()` also runs `nmap --script-help vulners` to confirm the `.nse` is actually installed, not just that `nmap` exists) and an execution method that runs the `subprocess`/parses the output (rustscan's greppable format, nmap's XML for fingerprinting and for CVE/CVSS, searchsploit's JSON). `ScanPhase` receives these four classes via dependency injection in `__init__` (with the real ones as defaults, plus `min_cvss=7.0`), which is what lets the whole orchestration be tested with fakes, with no subprocess at all (see `tests/test_scan_phase.py`).

Important: `vulners` isn't a separate `nmap` call — `VulnersTool.build_nmap_args(min_cvss)` returns `--script vulners --script-args mincvss=<min_cvss>`, which `ScanPhase` passes as `extra_args` to the same `NmapTool.fingerprint(...)` call that already does `-sV`. A single `nmap` process does fingerprinting and CVE correlation at the same time; `VulnersTool.parse_xml` then reads that same output XML file looking for the `<script id="vulners">` element per port.

If `searchsploit` isn't installed, the phase proceeds normally (it just skips exploit correlation). If `vulners` isn't installed, the phase also proceeds normally (it just skips CVE/CVSS correlation, and `searchsploit` goes back to running unconditionally, as before vulners existed). Only `rustscan` and `nmap` are actually mandatory for the `scan` command to work.

**Automatic installation of missing tools.** `InteractiveConsole._ensure_tool_available(tool_name, tool_cls, required)` (`view/console.py`) runs before any scan for `rustscan`/`nmap` (`required=True`, declining or failing the install aborts the scan) and `searchsploit` (`required=False`): it asks the user (`rich.prompt.Confirm.ask`) whether to install it now; if so, it calls `ToolInstaller.install(tool_name)` and checks again. `vulners` doesn't go through this ask-and-install flow (it has no automatable install — it's a standalone `.nse`, not a package): `handle_scan` just checks `scan_phase.vulners.is_available()` and, if `False`, prints a yellow warning with `ToolInstaller.manual_install_hint('vulners')` and proceeds with the scan normally (searchsploit covers the gap). `ToolInstaller` (`phases/scan/tools/installer.py`) only tries install paths that actually exist for each tool — `nmap`/`exploitdb` via apt/dnf/pacman/brew, `rustscan` via cargo/brew — and when none apply, or for `vulners`, it returns a manual-install hint (`manual_install_hint`) that the console shows. The install commands run via `subprocess.run` without capturing stdout/stderr on purpose, so a `sudo` password prompt shows up normally in the terminal.

The `Service` model (`model/service_model.py`) exists as its own table, separate from `Host.ports_active`/`ports_inactive` (which still exist for compatibility with the legacy monitoring flow), because correlating with exploit-db/vulners needs product/version per port — information the old fields (just a list of ports) don't store. `Vulnerability` (same file) stores `cve`/`cvss`/`reference` linked to a `Service`; the console shows these rows in their own table ("Vulnerabilities (CVE/CVSS via vulners)"), sorted by descending CVSS, only when there's at least one.

**`Service.name` — guessed service name for ports nmap can't fingerprint a banner for (2026-08-31, user-reported).** The user ran a real scan (ports 22, 631, 5601, 8220, 9200) and got a bare `?` in the Service column for every port where `nmap -sV` couldn't grab a banner (no `product`/`version`), even though the ports are recognizably Kibana/Fleet/Elasticsearch. Cause: nmap's XML always carries a `<service name="...">` attribute — its own best guess at the service, either confirmed by an actual version probe (`method="probed"`) or just looked up from nmap-services by port number (`method="table"`) — but `NmapTool._parse_xml` only ever read `product`/`version`/`extrainfo` off that element, silently dropping `name`. Fixed end to end: `ServiceFingerprint` (`phases/scan/tools/nmap_tool.py`) gained a `name: str | None = None` field (defaulted so existing positional call sites in tests/fakes keep working) populated from `service_el.get('name')`; `Service` (`model/service_model.py`) gained a matching `name` column, with `db/migrations.py` adding it to any pre-existing `sharingan.db` via `add_missing_columns`; `ScanPhase._persist_services` now passes `fingerprint.name` through. `view/console.py`'s three Service-column call sites (`command_services`, `command_vulns`, `handle_scan`'s scan-result table) changed their fallback chain from `product or '?'` to `product or name or '?'` — `name` is a lower-confidence, sometimes just-a-port-number-lookup signal, so it's deliberately still second-priority to a real probed `product`, and `'?'` remains the fallback for the rare case where nmap has neither. Tests: `test_nmap_tool.py` (`test_parse_xml_extracts_guessed_service_name_when_product_is_unknown`), `test_scan_phase.py` (`test_scan_phase_persists_guessed_service_name_when_product_is_unknown`), `test_migrations.py` (`test_run_lightweight_migrations_adds_service_name_column_on_legacy_schema`), `test_console.py` (`test_command_services_shows_guessed_service_name_when_product_is_unknown`, `test_command_scan_result_shows_guessed_service_name_when_product_is_unknown`, `test_command_vulns_shows_guessed_service_name_when_product_is_unknown`).

**Bug found while fixing the above: `db/migrations.py` was never actually wired in (2026-08-31).** `db/migrations.py` and its `run_lightweight_migrations()` existed, fully tested in isolation since the (reverted) per-distro CVE-verification work, but `db/database.py`'s `init_db()` only ever called `Base.metadata.create_all(bind=engine)` — which only creates tables that don't exist yet, never alters an existing one. `run_lightweight_migrations` was referenced from nowhere but `test_migrations.py`; it never ran against a real `sharingan.db`. This meant the user's own already-existing database (the one from the screenshot that started this fix) would never have gained the new `services.name` column, and the next `scan` would have crashed with `OperationalError: no such column: services.name` on the very first insert — silently defeating the fix above for exactly the person who needed it. Fixed by adding `run_lightweight_migrations(engine)` right after `create_all()` in `init_db()`. Regression test: `test_database.py` (`test_init_db_runs_lightweight_migrations_after_create_all`, new file — no prior coverage existed for `init_db()` at all).

**Explicit feedback when there's no finding.** On every run, `ScanPhase.run` records `self.last_vulners_enabled` (did the script run on this call?) and `self.last_searchsploit_ran` (did searchsploit actually run and finish?). `handle_scan` (`view/console.py`) uses these two flags after building the vulnerability/exploit tables: if the vulnerabilities table would be empty but `last_vulners_enabled` is `True`, it prints that vulners ran and found nothing relevant; the same applies to exploits with `last_searchsploit_ran`; and if `searchsploit` was skipped by design (vulners available, but nothing with CVSS above the minimum), the console explicitly says so instead of staying silent. This exists because, without this signal, "it ran and found nothing" and "it never even ran" were indistinguishable on screen — this was exactly the real confusion the user had running a scan (2026-08-30).

**searchsploit resilience (best-effort, must not take down the scan).** `searchsploit` is an optional step — but previously, a failure of it *at runtime* (not "not installed", but "installed yet broken", e.g. missing `xmllint`) propagated a `subprocess.CalledProcessError` all the way to `handle_scan`, which aborted the display of the whole scan, even with ports/services/vulnerabilities already persisted by nmap/vulners. `ScanPhase.run` now wraps only the call to `searchsploit` in a `try/except subprocess.CalledProcessError`, storing the message in `self.last_searchsploit_error` (`None` when there was no error) and leaving the rest of the result standing. `handle_scan` shows this error explicitly ("searchsploit failed to run: ...") instead of printing the "nothing found" message. This pattern — a failure in an optional tool must never throw away the result of an already-persisted earlier step — stands as a reference for any new optional step added in the future.

**Step-by-step progress (`on_progress`).** User request (2026-08-30): instead of a single static message ("Scanning...") sitting there until the whole scan finishes, each actual step (rustscan / nmap+vulners / searchsploit) should show up on the console as soon as it starts. `ScanPhase.run(self, name, target, on_progress=None)` accepts an optional callback called with a string right before each real subprocess: `"Scanning open ports (rustscan)..."`, then `"Fingerprinting services and versions (nmap -sV)..."` (or, with `vulners` available, `"...with CVE/CVSS correlation (nmap -sV + vulners)..."` — it's the same process call, the message just reflects that), and finally `"Looking up matching exploits (searchsploit)..."`, only when searchsploit is actually going to be attempted (if it's skipped because there are no open ports, or by design because vulners found nothing relevant, that last message doesn't show up — it makes no sense to announce a step that isn't going to run). `ScanPhase` knows nothing about `rich`/the console — the callback is just a `str -> None` function, which keeps the phase testable with no UI at all (`tests/test_scan_phase.py`, the `test_scan_phase_reports_progress_*` and `test_scan_phase_progress_*` cases, use `progress.append` as a fake). `InteractiveConsole._report_scan_progress(self, step)` (`view/console.py`) is the real callback, passed as `scan_phase.run(name=name, target=target, on_progress=self._report_scan_progress)`: it just prints `f"[*] {step}"`. The old, generic message became just an opening `"[*] Starting scan of <target>..."`.

When creating the next phase (e.g. `phases/recon/`), follow the same pattern: `PhaseModule` as the interface, external tools isolated in testable wrappers, orchestration via dependency injection, and progress via `on_progress` if the phase has more than one slow step.

**Considered and reverted: per-distro CVE verification (2026-08-30).** A `vulners` match is by CPE — product + *upstream* version (e.g. `OpenSSH 9.6p1`) — and it has no idea that Debian/Ubuntu apply security patches via backporting **without** bumping that upstream version; only the package's revision suffix (`-3ubuntu13.M`) changes with each fix. That makes `vulners` report as "vulnerable" any CVE whose upstream matches, even when the installed package has had the patch for several revisions already — confirmed with the user's own real case: `CVE-2026-60002` had already been fixed in Ubuntu since the exact revision the host had (`3ubuntu13.18`), and on top of that it's a CVE that only affects the SSH client, not the listening service the scan found.

A first version of a fix was built and fully tested: `UbuntuCveTool` queried `https://ubuntu.com/security/cves/<CVE>.json`, compared the installed version against Ubuntu's published fixed version via `dpkg --compare-versions` (orchestrating the distro's package manager instead of reimplementing Debian's version parser), and `ScanPhase` stored the result on two new `Vulnerability` columns (`verification_status`/`verification_detail`), shown as a colored column in the console tables. **The user then asked to remove it entirely** ("it would be a real headache for different [distros], and I don't think it's in scope for the project, not for now"), after a design discussion that surfaced real problems with generalizing it:

- It only ever covered Ubuntu/Debian (`dpkg`-based version comparison + `ubuntu.com`'s tracker). Every other distro family needs its own adapter: Debian's own tracker has no clean per-CVE JSON endpoint (only a full bulk dump to cache locally, unlike Ubuntu's tidy per-CVE API); RHEL/Fedora/Rocky/Alma need `rpm`-based comparison against Red Hat's own CVE/OVAL API; SUSE and Arch each have their own tracker and schema. Not a copy-paste per distro — a real adapter per family.
- **Portability bug for a shared/multi-user tool**: the version comparison shelled out to the `dpkg` binary on whichever machine *runs Sharingan* (not the scanned target) — so a user running Sharingan from Fedora/Arch/macOS would silently get no verification at all, even against a perfectly valid Ubuntu target, while a Kali/Debian-based user would. The fix on the table was swapping `subprocess.run(['dpkg', ...])` for the `python-debian` library's `Version` class (pure Python, no host-OS dependency) — never implemented, since the feature was pulled first.
- Reliability ceiling: this whole approach is an **unauthenticated, banner-based** check (trusting whatever `nmap` grabbed) — the same tier as `msfconsole`'s `CheckCode::Appears` (passive signal), never reaching `CheckCode::Vulnerable` (hard evidence from actively probing the live target), which needs per-CVE active-probe logic and is arguably active-exploitation territory anyway. A spoofed or generic banner fools this check exactly as it fools the underlying `vulners` match. True ground truth (what Nessus/OpenVAS do in *credentialed* mode, or `oscap`/OVAL tooling) requires real credentialed access to the target's actual package database, which a black-box `nmap` scan doesn't have.
- Certification framing the user cares about: the whole point of this check was to mirror what a human pentester would do manually (look up a CVE, read a changelog) rather than automate exploitation — a distinction that matters for exams like OSCP, which ban automated exploit-selection/chaining but generally allow this kind of passive recon aid. That framing is sound and worth keeping in mind for *any* future verification or exploitation feature, independent of whether this particular implementation shipped.

If this gets revisited, the natural shape is a small family of per-distro tools sharing one interface (`check(cve, product, version) -> {status, detail}`), selected by whatever distro name shows up in the nmap banner — same dependency-injection pattern `ScanPhase` already uses for its other tools. Until then, only the **Port**/**Service** columns from this work survive (see above) — no verification code remains in the tree.

**`hosts` / `services` / `vulns` commands (2026-08-30).** Directly inspired by msfconsole's commands of the same name (which list and delete data collected during a session), implemented in `view/console.py` (`command_hosts`, `command_services`, `command_vulns`) and registered in `self.cmds`/`self.completer`/`print_help`. They all follow the same syntax: no argument **lists**; `-d <addr>` **deletes only that host's data** (or only that host's services/vulnerabilities, in the case of `services`/`vulns` — the `Host` itself is only removed by `hosts -d`); `-d all` **deletes everything in that table, across all hosts**, and asks for confirmation first (`rich.prompt.Confirm.ask`, default `False`), via the shared `_confirm_delete_all` helper, because it can't be undone. `services`/`vulns` without `-d` also accept a host address as an optional filter (`services 192.0.2.10`) to list only that host's data; an unknown address in either command (`-d` or the listing filter) prints `"Host '<addr>' not found."` instead of silently showing nothing. `hosts -d <addr>` deletes the whole `Host`, which automatically cascade-deletes that host's `Service`/`Vulnerability`/`ExploitMatch` (see cascade delete above); `services -d <addr>` and `vulns -d <addr>` delete only the corresponding table, preserving the `Host` and (in the case of `services -d`) also preserving scan history if that's ever reintroduced — today `services -d` also cascade-deletes that service's `Vulnerability`/`ExploitMatch`, since they don't make sense without their parent service. Tests covering listing, filtering by host, deleting by host, confirmed/declined delete-all, and incorrect usage (`-d` without a target) are in `tests/test_console.py` (`test_command_hosts_*`, `test_command_services_*`, `test_command_vulns_*`). There's no separate `exploits` command yet — `ExploitMatch` can only be queried/deleted indirectly via `hosts`/`services`; adding a dedicated `exploits` command would be trivial following the same pattern, if the user asks for it.

**Exploit results grouped by service, with CVE cross-reference and a cap (2026-09-17, user-reported UX problem).** Real scan against the user's own `127.0.0.1` (OpenSSH, CUPS, PostgreSQL, Redis): the single "Exploits found" table mixed every service's hits together with no port/service indication, and `searchsploit`'s own text search returned every version of a product ever published — OpenSSH 9.6p1 got exploits for OpenSSH 1.2 through 9.8 all in one list (60+ rows for one scan). Fixed in two parts, both required correcting `ScanPhase._persist_exploit_matches`'s long-documented approximation ("every exploit goes to the host's first service" — pending item #7, now resolved):

- **Exploit↔service association is now exact, not approximate.** `SearchsploitTool.search_nmap_xml(xml_path)` (the old `searchsploit --nmap <xml>` mode) is gone, replaced by `SearchsploitTool.search_product(product)` (`searchsploit -t <product> -j`) — `ScanPhase.run` calls it once per persisted `Service`, using that service's own `product` (falling back to `name`) as the search term, so each `ExploitMatch` is written with the exact `service_id` it was searched for. This also **removes the `xmllint` dependency entirely** (confirmed: `--nmap` mode needed `xmllint` only to parse the XML file handed to it; a plain product-name search involves no XML at all) — `SearchsploitTool.is_available()` now only checks the `searchsploit` binary. Two bugs specific to this migration, both found via real-target verification (against `cve-2022-0543-redis-1` for Redis and the host's own `sshd`) before considering it done:
  - **`searchsploit -t` requires every word supplied to literally appear (whole-word match, not substring).** nmap's `product` field is frequently multi-word ("Redis key-value store", "PostgreSQL DB") — searching the full string verbatim returned **zero** results (confirmed: `-t "Redis key-value store"` finds nothing, `-t redis` finds the same 5 real matches `searchsploit redis` finds by hand). Fixed by searching only `product.split()[0]` — the same one-word-first behavior `--nmap` mode's own internal retry logic converged on anyway.
  - **nmap's `<service name="unknown">` is a literal placeholder, not a product name.** A port nmap can't fingerprint at all got searched as `-t unknown`, which matched totally unrelated exploits whose titles happen to contain the word "Unknown" (a LibTIFF DoS, a Windows COM privilege escalation, a Firefox/Safari one — for a port that turned out to just be a local VS Code process, see the earlier "where did postgres come from" investigation in chat history). Fixed by skipping the search when the term is `"unknown"` (case-insensitive), same as when there's no product/name at all.
- **Display groups exploits into one table per service** (`InteractiveConsole._print_exploit_table`, `view/console.py`), titled `"Exploits — port <N> (<product/name> <version>)"`, instead of one flat list. Rows are sorted with CVE-confirmed matches first, then exploit-db's own `Verified` flag, then title; capped at `EXPLOIT_DISPLAY_CAP = 10` with a `"+N more — run 'searchsploit <term>' for the full list."` note when there's more. The CVE cross-reference (`_exploit_matched_cve`) compares `ExploitMatch.cve_codes` — exploit-db's own `Codes` field, e.g. `"CVE-2008-3234;OSVDB-48791"`, persisted via two new columns on `ExploitMatch` (`cve_codes`, `verified`; migrated the same way as `services.name` was, via `db/migrations.py`) — against that same service's own `Vulnerability.cve` rows (already confirmed by `vulners`). **Deliberately not an exclusive filter**: verified empirically (again against the real Redis/OpenSSH scan) that exact CVE overlap between vulners and exploit-db is often zero even for genuinely relevant results — they're independent data sources with no guaranteed intersection — so an exclusive filter would leave the table looking empty most of the time. It ended up mattering in practice both ways in the same real scan: `CVE-2024-6387` (the "regreSSHion" OpenSSH CVE) correctly floated its matching exploit to the top of the port-22 table, while Redis/CUPS/PostgreSQL had zero CVE overlap and fell back cleanly to the sorted-and-capped list — exactly the intended degradation.
- Also considered and rejected: parsing version ranges out of exploit-db's free-text titles (`"< 7.7"`, `"2.x/3.x"`) to filter by the detected version. Same category of fragile heuristic the user already pulled back from once for the per-distro CVE-verification feature (see below) — titles have no consistent format, so it wasn't pursued.

Tests: `test_searchsploit_tool.py` (rewritten for `search_product`, `is_available()` without `xmllint`), `test_scan_phase.py` (`test_scan_phase_attributes_exploit_matches_to_the_correct_service`, `test_scan_phase_searches_only_the_first_word_of_a_multi_word_product`, `test_scan_phase_does_not_search_exploits_for_a_service_nmap_could_not_identify`), `test_migrations.py` (`test_run_lightweight_migrations_adds_exploit_match_cve_columns_on_legacy_schema`), `test_console.py` (`test_command_scan_groups_exploits_into_one_table_per_service`, `test_command_scan_shows_cve_confirmed_exploit_first_with_its_cve`, `test_command_scan_caps_exploit_rows_per_service_and_notes_how_many_are_hidden`).

## Development methodology: TDD (mandatory)

This project adopts Test-Driven Development as its main way of working. For any new feature or bug fix:

1. **Red** — first write a test in `src_sharingan/tests/` that expresses the desired behavior, and run it to confirm it fails (for the right reason).
2. **Green** — write the minimum code necessary in `core/`, `services/`, `model/`, `phases/`, etc. for the test to pass. Don't add behavior no test requires.
3. **Refactor** — with tests green, clean up duplication and naming without changing behavior. Rerun the tests after each refactor.
4. Always run the full suite (`uv run pytest`) before considering a task done — not just the new test.
5. For code that depends on real network/hardware/external processes (scapy/ARP, sockets, requests, whois, and now `subprocess` for rustscan/nmap/searchsploit), use mocks (`pytest-mock` / `unittest.mock`) or dependency injection with fakes, as in `test_scan_phase.py`. Never let a test depend on real access to the network, to an external target, or to a binary installed on the machine.
6. When touching a module with no coverage today, add at least one characterization test before changing its existing behavior (that's how the `view/console.py` bugs were fixed safely).
7. A deliverable isn't "done" without a corresponding test — including bug fixes (the test should reproduce the bug before the fix).

## Code conventions

- Python 3.12+, follow PEP 8 whenever possible. The legacy code has inherited inconsistencies (no need to rewrite it all at once), but new code should use `snake_case` for functions/variables and `PascalCase` for classes.
- Prefer type hints in new signatures (e.g. `ServiceFingerprint`, `ScanPhase.run(self, name: str, target: str) -> Host`).
- Comments, docstrings, and all user-facing console output (messages, table titles/columns, errors, usage/help text) must be in English. **Decision (2026-08-30, user request):** the project was originally written with Portuguese (pt-BR) comments and console text; the user asked for the whole codebase and console UI to be rewritten in English going forward, since he'd like to eventually share this as an open-source project. The full pre-existing codebase and test suite were translated in one pass on 2026-08-30 — comments, docstrings, and every printed string, but **not** Python identifiers or database column/field names (see note below). New code should be written in English from the start; don't reintroduce Portuguese.
- One known leftover from the translation: the `Host` model still has a field literally named `nome` (Portuguese for "name") — `model/host.py`, and used throughout (`scan_phase.py`'s `Host(nome=name, addr=addr)`, `view/console.py`'s `host.nome`, various tests). It was deliberately left alone during the translation pass because renaming a database column needs a real migration for anyone with an existing `sharingan.db` (the project has no Alembic — see the reverted CVE-verification note above for what happened last time a schema change without a migration story was attempted). Rename it to `name` only as an explicit, separate task with a migration plan, not as a drive-by fix.
- Never introduce real network scans/queries or subprocess calls that run automatically on module import.
- External tools (rustscan/nmap/searchsploit/future ones) always go behind a wrapper with `is_available()` and testable via dependency injection — never `subprocess.run` scattered directly in the middle of a service/phase.

## Ethical/legal considerations (offensive tool)

Sharingan is a pentest/reconnaissance tool. When generating code:
- Don't add active-exploitation features (exploits, credential brute-forcing, DoS) unless the user explicitly asks and makes clear the use is in an authorized environment.
- Keep responsible-use warnings in the documentation (use only against environments/targets you're authorized to test).
- Never let automated tests run scans, requests, or external processes against real targets — always mock/inject fakes.

- [x] Port scanning + service fingerprinting via external tools (`ScanPhase`: rustscan + nmap -sV).
- [x] Correlation with known exploits via `searchsploit`.
- [x] Ask and automatically install rustscan/nmap/searchsploit when missing (`ToolInstaller` + `_ensure_tool_available`).
- [x] CVE/CVSS correlation via the `vulners` NSE script (embedded in the same `nmap -sV` call), with `searchsploit` running unconditionally as a fallback when `vulners` isn't installed, or only for relevant findings (CVSS >= `min_cvss`) when it is.
- [x] Create `core/context.py` with `SessionContext`, replacing `SetEnvService` (2026-10-02).
- [x] Refine the exploit↔service association in `ScanPhase` (2026-09-17: searches per-service via `SearchsploitTool.search_product`, no longer "the host's first service" — see "Exploit results grouped by service" under "Phase architecture"). Also grouped the console display by service and added CVE cross-reference + a display cap to cut `searchsploit`'s text-search noise.
- [x] Decided (2026-08-29, at the user's request): **do not** automate downloading rustscan's `.deb` via the GitHub API. `ToolInstaller.install_rustscan` intentionally stays cargo/brew-only — dynamically downloading and installing (`dpkg -i` as root) a third-party binary in an offensive tool is a different trust surface than using the distro's package manager, and besides, it would only cover apt systems anyway (it would never work on an isolated/air-gapped network, which is common in real engagements). Anyone with `cargo` installed already solves it in one command; everyone else follows the manual link. Don't reopen this without the user asking again.
- [ ] New phase: Recon (whois already exists as a standalone command — consider moving it to `phases/recon/`; subdomains).
- [ ] File/directory fuzzing (a future phase, probably orchestrating an existing tool, e.g. ffuf/gobuster, instead of reimplementing one).
- [ ] Resource monitoring (CPU/memory).
- [ ] Future: web layer (API/dashboard).
- [x] Decided (2026-08-30, at the user's request): full pt-BR → English rewrite of comments, docstrings, and console output, since the project may be shared on GitHub. See "Code conventions".
- Considered, prototyped, then reverted (2026-08-30, at the user's request): per-distro CVE-verification cross-check (`UbuntuCveTool`) — see "Considered and reverted: per-distro CVE verification" under "Phase architecture" for the full design discussion and what a future attempt should account for.
- [ ] Future: a `ShellPhase`/`ExploitPhase` integrating with [Penelope](https://github.com/brightio/penelope) for reverse-shell handling, once the scan/recon side is solid (user's stated long-term direction, 2026-08-30). Design principle to carry into it: any phase beyond Scan that can actually run an exploit or open a shell must require an explicit human confirmation in the middle (the same `Confirm.ask` pattern `_ensure_tool_available` already uses) — never an automatic recon → exploit → shell chain. This keeps Sharingan in the "assists a human's manual workflow" category rather than "automated exploitation," which matters both ethically and for compatibility with certification exams (e.g. OSCP) that ban automated exploit-selection/chaining tools.
